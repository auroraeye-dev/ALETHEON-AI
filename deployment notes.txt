=== DEPLOYMENT — STORAGE / VECTOR STORE (logged 2026-05-28) ===
FOUNDER NOTE TO SELF: when deploying, BUY/PROVISION STORAGE and host the vector
store there — i.e. vectorize INTO persistent deployed storage, not the local disk.

WHY THIS MATTERS:
- Right now Qdrant runs EMBEDDED/LOCAL (data/qdrant/ on the laptop). That's perfect
  for a prototype but does NOT survive a cloud deploy: most hosts (Render/Railway/
  containers) have EPHEMERAL disks — the qdrant folder gets wiped on every restart/
  redeploy, so you'd re-embed from scratch every time (slow + re-pays embedding cost).
- On deploy you need PERSISTENT storage for the vectors. Options:
    1. Managed Qdrant Cloud (easiest — swap the embedded client for a hosted URL+key;
       our storage/vectorstore.py is the ONLY file that changes).
    2. A persistent volume / disk attached to the host (mount data/qdrant/ to it).
    3. Another managed vector DB (Pinecone, Weaviate, pgvector on managed Postgres).
- COST PLANNING: embeddings are cheap per-run but storage + re-embedding at scale adds
  up. Budget for: (a) vector DB storage (grows with #drugs × #chunks), (b) re-embedding
  only when source data changes (the E3 cache already avoids needless re-fetch; a
  persistent vector store avoids needless re-embed).

ARCHITECTURE IS ALREADY READY FOR THIS:
- vectorstore.py is cleanly isolated — switching from embedded Qdrant to hosted Qdrant
  is basically a connection-string change, not a rewrite. Good separation pays off here.
- Keep data/ gitignored (already done). Vectors live in the DB, not the repo.

ACTION AT DEPLOY: provision persistent vector storage FIRST, point vectorstore.py at it,
verify a drug persists across a restart (ingest once, restart, confirm search still
returns without re-embedding).
